Victor dropped X-CUBE-53L9A1 into the repo root. Task: track it, and evaluate whether it
carries what the Nordic port needs.

## What was done

- Copied the two BSD-3-Clause components into the repo, byte-identical:
  - `Drivers/BSP/Components/vl53l9/` → `firmware/drivers/vl53l9cx/st/`
  - `Utilities/vl53l9-common/` → `firmware/drivers/vl53l9cx/st-reference/`
  - Provenance and licensing recorded in a `PROVENANCE.md` beside each.
- Left the SLA0111 middleware and NUCLEO projects, and the 35 MB of STM32H5 HAL and
  CMSIS, out of the repo.
- Wrote `docs/plan/st-package-audit.md`; corrected `driver-port.md`,
  `frame-rate-budget.md`, `sensor-vl53l9cx.md` and the driver README.

## Answer to the question asked

Yes — it has everything stage 1 needs, and more than expected. `vl53l9.h` exposes power
modes, single-shot capture, two on-device configurations, per-frame health telemetry and
a query for the exact buffer size per binning mode. None of that was in the plan.

## Three things it broke

1. **The platform scaffolding follows the wrong driver generation.** VL53L9 is not the
   L5/L8 ULD carried forward. Thirteen functions, not six; `int` not `uint8_t`; opaque
   `p_dev`; sized accessors called directly; no `SwapBuffer`; three board-config
   getters. Rewrite required, and it is the next task.
2. **54×42 frames are 14,842 bytes, not 13,608.** Missed the DSS array and the status
   line. ~404 ms at 400 kHz.
3. **The mode span is 72.8×, not ~150×.** A fixed 100-byte status line dominates the
   smallest mode — half the traffic at 4×4.

## Worth remembering

The thing that looked most alarming turned out to be nothing, and the thing that looked
like a detail turned out to matter. ST's reference platform port is written entirely
against `HAL_I3C_*`, which reads as an I3C-only driver and would have invalidated the
I²C decision. It does not: every transfer uses the peripheral's *legacy I²C
private-transfer* mode, so the wire protocol is ordinary I²C. Meanwhile
`vl53l9_get_config_vdda/vddio/ext_clock` — three getters easy to skim past — are called
by `vl53l9_init()` and written into the device, which promotes the schematic from a
convenience to a blocker.

The address question got worse, not better. ST defines `VL53L9_DEFAULT_ADDRESS (0x52)`
and passes it into a HAL field documented as 7-bit; the community Python driver uses
0x29 7-bit and demonstrably works. One is a shift error. A bus scan settles it.

# 2026-09-01 (later) — the port itself

Victor asked to prepare the driver for the Nordic port while the supply values are
still outstanding. Everything except those three values is knowable from ST's source,
so the whole of stage 1 got written.

## What exists now

- `vl53l9cx_platform.c` — ST's thirteen functions on Zephyr I2C.
- `vl53l9cx.c` — init, PM actions, resolution handling, frame unpacking.
- `vl53l9cx_private.h` — config and data structs.
- Rewritten binding with the three required board values, plus `clock-pwms`.
- Corrected public API and the old `vl53l9cx_platform.h` deleted.

## The one thing to be clear about

**It has never been compiled.** No C toolchain on this machine — checked for gcc,
clang, cl, and the ARM toolchains, and for an `ncs` workspace. None present. So the
honest claim is: every ST symbol the driver calls was checked by hand against
`st/vl53l9.h` and `st/vl53l9_platform.h`, and the frame layout and byte counts were
read out of ST's source rather than estimated. Whether it builds is unknown.

## Things found while writing it

**The address is settled.** `vl53l9_set_com_config()` writes `address >> 1` into the
device register and `get_com_config()` reads it back shifted left. ST's `address` field
is the 8-bit form throughout, so 0x29 is the 7-bit address and their STM32 sample
passing 0x52 into a 7-bit HAL field is a bug in the sample. The VERIFY opened this
morning is closed.

**The frame is plane-major.** Depth plane, amplitude plane, ambient plane, then DSS,
then the status line — not three words per zone, which is what an earlier comment in
the public header claimed. That mistake would have produced a frame that looked almost
right, which is the worst kind.

**The status line is ST's `vl53l9_meta_t`,** and it carries a device-side frame counter.
Comparing it against the driver's own count separates "we dropped a frame" from "the
sensor never produced one" — a distinction that is otherwise invisible and exactly the
sort of thing that wastes a day at bring-up.

**The old API could not express the use case.** `vl53l9cx_start()` took a rate as
`uint8_t hz`; room dwell wants 0.05-0.2 Hz. Changed to a period in milliseconds, and
added `vl53l9cx_capture()` for the single-shot path that makes the low duty cycle
possible at all.

**PWM probably cannot make 12 MHz.** If the MCU has to source AP_CLK, a 16 MHz base
divides to 16, 8 or 5.33 — not 12. The legal range is 6-27 MHz, so 8 MHz may be the
cheap answer, but this needs the schematic before it needs a solution.

## Judgement call to flag

`vl53l9_read_async()` returns an error rather than silently doing a synchronous read.
A stub that "works" would let a caller believe a transfer is in flight, read the buffer
early, and get a torn frame that looks like a sensor fault. Failing loudly is worth
more than a hollow completeness here, and the synchronous frame path is complete.

# 2026-09-01 (later still) — board file, app, and 8 MHz

Victor asked for a port file handling all I2C traffic as the driver/board interface, a
board file, and AP_CLK at 8 MHz.

The port file already existed — `vl53l9cx_platform.c` is exactly that interface, and it
is now four traps rather than three (see below). What was missing was everything around
it, so: a board definition, a bring-up app, a west manifest.

## 8 MHz is the right number, not a compromise

The sensor takes 6-27 MHz. A 16 MHz PWM base divides to 16, 8, 5.33. ST's reference
12 MHz is unreachable; 5.33 is below the minimum. **8 MHz is the only exact frequency in
the legal window**, which is a satisfying result — the constraint picked the value.

The remaining risk is that 8 MHz needs COUNTERTOP = 2 and a one-tick duty, and some nRF
PWM hardware wants COUNTERTOP >= 3. If so, no other frequency helps and the answer is a
different mechanism: TIMER + GPIOTE/DPPI, or an oscillator on the board. Flagged in the
DTS at the point where someone would look.

## What is honest about the board file

Structure, driver wiring, address, bus speed and clock are real. Every pin number is a
placeholder. VDDA and VDDIO are ST's reference values, not this board's. And the
peripheral instance names are probably wrong — the nRF54L15 numbers serial peripherals
by power domain, so `i2c1` does not exist; `i2c21` stands in.

Rather than hope that gets noticed, gate 0 of the app prints VDDA, VDDIO, AP_CLK and the
address from devicetree before touching the sensor. A wrong placeholder shows up in the
first line of console output instead of being diagnosed hours later as a sensor fault.

## Small design calls

- Sensor rail is `power-gpios`, not a `regulator-fixed` node: the driver already
  sequences it against XSHUT and AP_CLK, and a regulator would put a second consumer on
  the same pin.
- The driver now selects PWM unconditionally. A conditional select on `clock-pwms` was
  more correct and depended on a Kconfig preprocessor function whose exact name I could
  not verify — the wrong trade for code that has never been built.
- The app's power cycle goes SUSPEND -> TURN_OFF and TURN_ON -> RESUME. Zephyr's device
  PM rejects TURN_OFF from ACTIVE, so the shorter version would silently do nothing.
