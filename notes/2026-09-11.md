# 2026-09-11 — WORKING VERSION: 54x42 full resolution

Confirmed on Victor's bench. The VL53L9CX ranges at the full 2268-zone array on the
custom `water_sense_board`. This file records the configuration exactly, so the build
can be reproduced without reading a diff.

**Tag:** `working-54x42-2026-09-11` -> commit `d83ad03`, which is the exact firmware
tree that was flashed. Everything after it is documentation.

```bash
git checkout working-54x42-2026-09-11
west build -b water_sense_board/nrf54l15/cpuapp firmware_test --pristine
west flash
```

## The configuration that works

| | | Where |
|---|---|---|
| Resolution | **54x42**, 2268 zones, binning 2 | `CONFIG_APP_TOF_RES_54X42=y`, prj.conf |
| Exposure | **4 ms** | `CONFIG_VL53L9CX_EXPOSURE_MS=4` |
| **AP_CLK** | **12 MHz, external crystal** | `ext-clock-frequency = <12000000>` in the app overlay |
| GRTC clock output | **deleted** — the SoC does not drive AP_CLK | `/delete-property/ clkout-fast-frequency-hz` |
| I2C | 400 kHz, SCL P1.08, SDA P1.13, 4.7 kOhm external pull-ups | board file |
| I2C buffers | 1040 B concat + flash-buf | `&i2c21`, app overlay — without these the firmware blob upload returns -ENOSPC |
| I2C timeout | 2000 ms | `CONFIG_I2C_NRFX_TRANSFER_TIMEOUT=2000` |
| Sensor power | P0.02, held high by the app | `CONFIG_APP_HOLD_SENSOR_POWER=y` |
| XSHUT / INT | P1.07 / P0.01 active low | app overlay |
| DVDD | 1.2 V | measured, Victor |
| Register writes | exposure ON, DSS LUT ON, profile ON | all three `=y` |
| Main stack | 4096 | immediate-mode logging formats on the calling stack |
| RTT up-buffer | 32768 | one full grid is ~9 KB and arrives as a burst |
| MPU | off | `CONFIG_ARM_MPU=n`, Victor 2026-09-04 |
| SDK | nRF Connect SDK v3.3.0 | `west.yml` |

Build size: **FLASH 77,484 B (5.30%), RAM 77,376 B (40.19%)**.

## Two switches that are ON and must come OFF before any energy measurement

Both are marked TEMPORARY in Kconfig and both invalidate power numbers:

- `CONFIG_VL53L9CX_EXPOSURE_BACKOFF=y` — halves exposure on each laser fault. A sensor
  that quietly reduces its own exposure is not a measurement instrument. It is on
  because the intermittent `0x0F00` faults are not yet explained, and the exposure it
  settles at is the number that would explain them.
- `CONFIG_VL53L9CX_HOLD_HFCLK=y` — holds HFXO continuously and never releases it. Idle
  current under this build is meaningless.

## What is NOT measured

Nothing from 54x42 is recorded: no amplitude, no valid-zone count, no frame time. The
one that decides something is **per-zone amplitude at binning 2 against the 126 measured
at 24x20 on this same day**. Binning 4 -> 2 is a quarter as many SPADs per zone, so ~32
is the prediction. That answers whether full resolution carries usable SNR, and so
whether the paper's resolution axis is a real axis.

## Still open
- Intermittent `ERROR_CODE 0x0F00` (CABDT LDD fault) after the clock fix. Consistent
  with a VCSEL supply marginal at high shot current — the original hypothesis, now
  without the clock confound.
- The IMU at 0x6B, silent since 2026-09-10. A clock change should not affect it.
- 4.7 kOhm pull-ups are already out of spec at 400 kHz (t_r = 0.8473*R*C against the
  300 ns limit). 1 kOhm, and a precondition for Fast-mode Plus.
